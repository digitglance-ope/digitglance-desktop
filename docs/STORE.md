# Microsoft Store (MSIX) — DigitGlance Trade, Books and School

**Decision (owner):** Windows customers get the apps from the **Microsoft
Store as MSIX packages**. Microsoft signs each package when it publishes it, so
**we do not buy a code-signing certificate**. The direct-download NSIS installer
and the GitHub self-updater (`release-products.yml` / `promote-latest.yml`) stay
as they are, for anyone who installs from the website.

| | Store (MSIX) | Direct download (NSIS) |
|---|---|---|
| Built by | `.github/workflows/store-msix.yml` (manual) | `.github/workflows/release-products.yml` (tag) |
| Signed by | Microsoft, at publication | nobody yet (SmartScreen warning) |
| Updates | Microsoft Store | Tauri updater from `<product>-latest/latest.json` |
| Cargo feature | `--features store` (updater not registered) | default |
| Config overlay | `tauri.<product>.conf.json` + `tauri.store.conf.json` | `tauri.<product>.conf.json` |
| Version | `X.Y.Z.0` (from app `X.Y.Z`) | `X.Y.Z` |

## Why MSIX (the facts this rests on)

- The Store re-signs MSIX packages with a Microsoft certificate after
  certification: "You don't need to purchase a CA-trusted code signing
  certificate for MSIX/AppX Store submissions." MSI/EXE submissions are **not**
  re-signed and must be Authenticode-signed by us.
  ([App package requirements for MSIX apps](https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/msix/app-package-requirements))
- The same page: the fourth part of the version "is reserved for Store use and
  must be left as 0", and the first part cannot be 0. We map app `1.0.2` →
  MSIX `1.0.2.0`. Pre-release versions (`1.0.3-beta`) are rejected.
- An MSIX installed outside the Store (sideloading) must be signed by us. That
  is what the **TEST** package below is for, using a throwaway certificate.
- Tauri's own Store guide covers only submitting the EXE/MSI (it needs our own
  signing certificate and `webviewInstallMode: offlineInstaller`), and Tauri has
  no MSIX bundle target. So we build the plain binary and package it ourselves.
  ([Tauri: Microsoft Store](https://v2.tauri.app/distribute/microsoft-store/))

## How the package is made

`store-msix.yml` (Actions → **Microsoft Store (MSIX)** → Run workflow; choose
product, optional version, optional arm64):

1. **prepare** (Ubuntu): runs the generator tests (`npm run test:msix`), turns
   the version into `X.Y.Z.0`, and checks that the Store identity is set.
2. **package** (windows-latest, x64 and optionally arm64):
   - `npx tauri icon` → `src-tauri/icons/<product>` (the exe icon);
   - `tauri build --config tauri.<product>.conf.json --config tauri.store.conf.json
     --features store --no-bundle --target <triple>`: the plain app binary,
     **with no updater**;
   - `node scripts/msix/cli.mjs layout ...` writes the package layout:
     `AppxManifest.xml`, the exe renamed to `DigitGlance<Product>.exe`, and
     `Assets/` generated from `assets/<product>-icon-source.png` (the same
     source as `src-tauri/icons/<product>`);
   - `makeappx pack` (Windows SDK, preinstalled on the runner).
3. **bundle** (only with arm64 + identity set): `makeappx bundle` →
   `<product>-<version>-store.msixbundle`.

### Artifacts

| Artifact | What it is | Use |
|---|---|---|
| `<product>-<version>-x64-store` → `<product>-<version>-x64-store.msix` | **Unsigned**, real Store identity | Upload to Partner Center |
| `<product>-<version>-store-bundle` → `.msixbundle` | x64+arm64 (if requested) | Upload instead of the single .msix |
| `<product>-<version>-x64-TEST-ONLY` → `-test.msix`, `<product>-TEST-ONLY.cer`, `README-TEST-ONLY.txt` | Signed with a self-signed cert made in that run; identity `DigitGlance.<Product>.TestOnly`, name "DigitGlance <Product> (TEST ONLY)" | Sideload on a POS/test machine. **Never give it to customers** |

The Store package is built only once the identity is configured (below). The
TEST package always builds, so you can try MSIX before Partner Center is set up.
It uses a different identity from the Store app, so the two install side by side
and do **not** share data.

### The manifest

Generated by `scripts/msix/manifest.mjs` (do not hand-edit the output):

- `Identity Name / Publisher / Version (X.Y.Z.0) / ProcessorArchitecture`
- `Properties`: DisplayName (the reserved Store name), PublisherDisplayName, Logo
- `TargetDeviceFamily Name="Windows.Desktop" MinVersion="10.0.17763.0"`
  (Windows 10 1809, the Desktop Bridge floor), `MaxVersionTested="10.0.26100.0"`
- `Application Executable="DigitGlance<Product>.exe" EntryPoint="Windows.FullTrustApplication"`
- `uap:VisualElements`: Square44x44Logo, Square150x150Logo, DefaultTile
  (Wide310x150Logo, Square71x71Logo, Square310x310Logo), SplashScreen; StoreLogo
  in Properties. Sizes: 44, 50, 71, 150, 310, 310x150, 620x300 at scale-100.
- Capabilities: `internetClient`, `rescap:runFullTrust`.

`runFullTrust` is a **restricted capability**: Partner Center asks you to
justify it during submission. Suggested text: *"DigitGlance is a packaged
Win32 desktop application (Tauri/WebView2) and needs full trust to run as a
standard desktop process."*

### Store identity: build inputs, never invented

The values come from Partner Center after you reserve each name (App →
**Product management → Product identity**). Values are case- and
space-sensitive. Set them as **repository variables** (Settings → Secrets and
variables → Actions → **Variables**). They are not secret; every published
package carries them.

| Variable | Partner Center field | Notes |
|---|---|---|
| `MSIX_PUBLISHER` | Package/Identity/Publisher | `CN=XXXXXXXX-...`; same for all three apps |
| `MSIX_PUBLISHER_DISPLAY_NAME` | Package/Properties/PublisherDisplayName | e.g. the company name as registered |
| `MSIX_TRADE_IDENTITY_NAME` | Package/Identity/Name (Trade app) | e.g. `12345DigitglanceReliance.DigitGlanceTrade` |
| `MSIX_BOOKS_IDENTITY_NAME` | Package/Identity/Name (Books app) | |
| `MSIX_SCHOOL_IDENTITY_NAME` | Package/Identity/Name (School app) | |
| `MSIX_<PRODUCT>_DISPLAY_NAME` | the reserved name | Optional; only if it is not "DigitGlance <Product>" |

Alternatively, fill `msix/store-identity.json` and commit it. Repository
variables win over the file. A value that starts with `REPLACE_ME` counts as
unset.

## WebView2 (the trade-off)

Tauri renders through the Microsoft Edge **WebView2 Runtime**. Tauri's
`bundle.windows.webviewInstallMode` only affects the NSIS/MSI installers, and an
MSIX cannot run an installer during install. The options:

| Option | Package size | Behaviour |
|---|---|---|
| **Rely on the preinstalled Evergreen runtime** (chosen) | ~10 MB | Runtime is part of Windows 11, and Microsoft says "the vast majority of Windows 10 devices have the WebView2 Runtime installed already". Updated by Microsoft with security fixes. |
| Bundle a Fixed Version runtime inside the package | +~180 MB (Tauri), "over 250 MB" unpacked (Microsoft) | Works with no runtime installed, but **we** must ship a new package for every WebView2 security fix, and every update download grows by that much. |
| `win32dependencies:ExternalDependency` | — | Only honoured by App Installer sideloading, not by Store installs. |

Sources: [WebView2 distribution](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution),
[Tauri Windows installer: WebView2 options](https://v2.tauri.app/distribute/windows-installer/).

**Decision: Evergreen.** On the rare Windows 10 machine without WebView2, the
app fails to open its window. Fix: install the runtime from
<https://developer.microsoft.com/microsoft-edge/webview2/consumer/> or with
`winget install Microsoft.EdgeWebView2Runtime`. Put this line in the Store
listing's **system requirements** and in support notes. Follow-up: a Store-only
startup check that shows a friendly message with that link instead of a silent
exit. It needs a Windows API crate, so it should land when a Rust toolchain is
available to test it.

## Behaviour differences you must know (MSIX runs in a container)

1. **Uninstall deletes local data.** For a packaged app, new files under
   `%AppData%`/`%LocalAppData%` go to a private per-package location, and "when
   a package is uninstalled ... any redirected writes to AppData or the registry"
   are removed.
   ([How packaged desktop apps run](https://learn.microsoft.com/en-us/windows/msix/desktop/desktop-to-uwp-behind-the-scenes))
   Today the shell keeps no business data locally (only WebView2 cookies/cache),
   so uninstalling just signs the user out. **For the coming offline POS (local
   SQLite holding unsynced sales) this becomes a data-loss risk:**
   - **Rule:** never uninstall or reset a POS install that has pending sales.
     Sync first. Support staff must check the pending-sales count before telling
     a shop to "reinstall the app".
   - **Planned in the offline programme:** a visible pending-sales counter, an
     **"Export pending sales"** safety action (file saved outside the package,
     e.g. Documents, which is not virtualised), and a warning in the app before
     sign-out/reset when unsynced sales exist. Windows shows no app-controlled
     prompt on uninstall, so the warning must live in the app and the
     shop-owner guide.
   - Updates (Store or sideload) keep the data. Only uninstall or "Reset" in
     Settings → Apps clears it.
   - The TEST package and the Store package are different identities with
     separate data stores. Data does not carry over between them.
2. **No self-update in Store builds.** `--features store` leaves
   `tauri-plugin-updater` unregistered (`src-tauri/src/lib.rs`), and
   `tauri.store.conf.json` empties the endpoints as a second guard. The shell
   has no "check for updates" UI. The Store updates the app.
3. **Store updates wait while the app runs.** Windows defers servicing a
   package that is in use until it exits
   ([Inside MSIX: servicing while in use](https://devblogs.microsoft.com/insidemsix/msix-servicing-while-in-use/)).
   A till left open for weeks keeps the old shell. Ask shops to close the app at
   end of day. The web content is live anyway, so shell updates are rare.
4. **Getting the app onto POS machines.** Machines need Microsoft Store access,
   or `winget install --source msstore <StoreId>`, or Intune/Company Portal for
   managed fleets. Locked-down PCs with the Store blocked by policy cannot
   install it. Keep the NSIS download as the fallback for those.
5. **Install location is read-only** (`C:\Program Files\WindowsApps\...`). The
   shell never writes next to its exe, so nothing changes for it.

## Owner checklist (Partner Center)

1. **Register a company developer account** at
   <https://developer.microsoft.com/en-us/store/register> (leads to Partner
   Center) as **Digitglance Reliance**. Microsoft
   removed the company onboarding fee in May 2026: "The $99 onboarding fee for
   company developer accounts has been removed"
   ([Windows Developer Blog, 7 May 2026](https://blogs.windows.com/windowsdeveloper/2026/05/07/publish-to-microsoft-store-as-a-company-now-with-free-registration-and-faster-onboarding/)).
   The older enrolment page may still show $99, so check what the sign-up flow
   charges. You need: a work account (Microsoft Entra ID), a business-domain
   email, and business verification. A D-U-N-S number is fastest. Otherwise
   upload CAC documents (certificate of incorporation, status report).
   Verification appeals are limited to three attempts, so make the details
   match CAC exactly.
2. **Reserve the names:** "DigitGlance Trade", "DigitGlance Books",
   "DigitGlance School" (or your choice; if different, set
   `MSIX_<PRODUCT>_DISPLAY_NAME`).
3. **Copy the Package Identity** values (Name, Publisher, PublisherDisplayName)
   into the repo variables above.
4. **Try the TEST package first** on a real POS machine. Use the steps in
   `README-TEST-ONLY.txt` inside the artifact: import the `.cer` into
   *Local Machine → Trusted People* as admin, then `Add-AppxPackage`. Check
   sign-in, POS flows, printing, the offline page, and uninstall/reinstall.
   Remove the certificate afterwards.
5. **Run the workflow** for the product and version. Download
   `<product>-<version>-x64-store.msix` (or the `.msixbundle`).
6. **Create the submission:**
   - *Packages*: upload the `.msix`/`.msixbundle`. Partner Center validates the
     identity. A mismatch means a variable is wrong.
   - *Restricted capabilities*: justify `runFullTrust` (text above).
   - *Store listing*: description, screenshots (at least 1; 1366x768 or larger),
     the logo, system requirements (mention WebView2), and the support contact.
   - *Age ratings*: complete the IARC questionnaire (business software, no user
     content to minors).
   - *Privacy policy URL*: `https://digitglance.com/privacy` (the live page,
     `apps/frontend/src/app/privacy` in the platform repo). It is required
     because the app uses the internet. School can use the same URL.
   - *Pricing/availability*: free download (subscriptions are sold on the web).
     Choose the markets.
   - *Notes for certification*: the app is a desktop client for
     digitglance.com and requires sign-in. **Put a working demo login in this
     Partner Center field only. Never commit credentials to this repo.** Add a
     sentence on what reviewers should try (e.g. "sign in, open POS, add an
     item, complete a cash sale").
7. **Every later update:** bump the version in `tauri.<product>.conf.json` (or
   pass it to the workflow). It must be higher than the previous Store
   submission. Then run the workflow, upload, and submit.

## Caveats and open items

- **Not built yet:** this machine has no Rust toolchain, so the first workflow
  run is the end-to-end gate. Locally verified: the generator tests, `makeappx
  pack` + `makeappx bundle` on generated layouts (schema validation), signing a
  TEST package with a self-signed cert via `signtool`, and actionlint on every
  workflow.
- **Exe name in the Tauri output:** the workflow takes `<productName>.exe` or
  `digitglance.exe` from `src-tauri/target/<triple>/release/`, whichever
  exists. If a Tauri upgrade changes that, the "Locate the built exe" step fails
  loudly.
- **Logos are scale-100 only** (no `resources.pri`), so tiles may look soft on
  high-DPI screens. Follow-up: generate scale-200/400 + `targetsize` variants
  and run `makepri`.
- **Store policy on web wrappers:** like Google Play, Microsoft can reject apps
  that only wrap a website. The listing should present the dedicated window,
  offline gate and (soon) offline POS as native value.
- **arm64** builds are opt-in and untested.
- The shell's `?client=<product>-desktop` isolation and School's no-billing rule
  apply unchanged to the Store builds (same `dist/<product>` pages). The Store
  listing for School must not advertise in-app purchases.
